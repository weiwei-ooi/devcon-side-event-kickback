## The mechanism (decided with Wei Wei)
- Guests choosing the Committed Spot send the **ETH deposit** on **Ethereum mainnet** from their own wallet to the deposit contract, then paste the tx link (etherscan.io) on Luma.
- We verify each deposit on-chain (the contract's `Deposited` events). **Wei Wei curates every guest herself, paid or free** (bots get declined). Only guests who are verified **and** approved on Luma are registered in the contract. Paying guests she declines get exactly their deposit back (`rejectAndRefund`, the "Refund declined guests" button); we never keep their money.
- Claude exports the Luma guest CSV (Chrome, manage page) and prepares the lists; she does not export it herself.
- After the event, every staker who **checked in** gets an equal share of the **whole** pool: their deposit back plus a share of the no-shows' deposits. No-shows lose their deposit.
- **Kleros challenges (her request, 25 Oct; mechanism in her words):** the organiser publishes the attendance list; any staker left off has **1 day** to put a challenge deposit (ETH = Kleros fee, about 0.0162 ETH on Ethereum mainnet today); anyone has **1 day** to match it, otherwise the staker counts as attended; a matched challenge creates a Kleros dispute; payouts only when no dispute is pending (since v4, F7: payouts go ahead and one share per open case is set aside). Since v6 (27 Oct) this runs on **Kleros Court v1 on Ethereum mainnet**, through Kleros's general-purpose Dispute Resolver (ArbitrableProxy) `0x4b89e798b10478a839ea0abcf86c4b94a3c782a4`, whose arbitrator is KlerosLiquid `0x988b3A538b618C7A603e1c11Ab82Cd16dbE28069`: General Court (0), 3 jurors, about 3 weeks per round (evidence 78 h, commit 162 h, vote 162 h, appeal 108 h). (v3 to v5 used the Kleros v2 DisputeResolver on Arbitrum One; Kleros v2 is Arbitrum-only.) Juror policy `docs/attendance-policy.md` must be pinned on IPFS and set as `kleros.policyURI` before the live deploy. **Since v7 (28 Oct, her request) each case has its own description** (ERC-1497 metaevidence naming the event, the wallet, the deposit and the contract, `fileURI` = the policy): the contract writes it from `docs/metaevidence.template.json` (filled in and fixed at deploy) and computes its IPFS path on-chain (`caseMetaEvidence(staker)`); the console and guest page upload the file to Kleros's IPFS service at match time. Policy and template are fixed in the contract at deploy. Mention the feature on Luma.

## How to run things
```bash
npm install && npm run compile      # first time
npm test                            # optional, ~4 min
npm run console                     # local copy of the organiser panel (her rule: use the online /organiser/ page instead)
npm run console:rehearsal           # throwaway contract on Ethereum mainnet, 0.25 ETH cap
```
**During registration:** export the Luma guest CSV yourself (Manage → Guests → export) and run:
```bash
node scripts/verify-deposits.mjs --guests <file>.csv --scan-from-block <deploy block>
```
It sorts verified payers by her Luma decision: `out/to-review.csv` (waiting for her), `out/new-stakers.json` (approved → she clicks **Register stakers**), `out/refunds.json` (declined → she clicks **Refund declined guests**). `out/issues.csv` has plain-language codes for guests to email; `out/unmatched.csv` lists deposits nobody claimed and `out/returns.csv` every other amount to give back (short, overpaid, late, paid twice), both net of returns already made: she returns them with **Return a stray transfer**. The script refuses to run on a real network without a deploy block. Public RPCs only serve old logs in small ranges, so log scans run in `logChunk` blocks (5,000) with retries.

**After the event:** export the CSV again (`checked_in_at` is filled at the door) and run:
```bash
node scripts/build-payout.mjs --checkins <file>.csv [--extra-checkins door-list.csv]
```
Before that, make sure every payer still pending, waitlisted or late has been declined on Luma and refunded (**Refund declined guests**). Show her `out/payout-summary.md`. She clicks **Post attendance list**, which reads `out/payout-plan.json` and refuses if the numbers on-chain changed. That opens the 1-day challenge window: watch the challenge list with her (she can **Add to the list** before anyone matches, **Dispute**, or let it run). **Dispute** first uploads that case's own description (event + wallet) to Kleros's IPFS service; check the challenge list shows it as published (**Publish case description** retries). "Challenge details" evidence is optional. After the window, once no challenge waits for a match, she clicks **Release payouts** (one share per open Kleros case is set aside; unmatched expired challenges are settled one by one first). Watch for appeal funding of "refuse to arbitrate" (0) too: funded alone, it wins and counts as did not attend. **Watch every open case's appeal window** and fund her side with **Fund appeal** if the other side funds an appeal (an unanswered appeal wins the case); send evidence with **Submit evidence**; after the final ruling: **Deliver final ruling** if Kleros's bots haven't (KlerosLiquid `passPeriod` then `executeRuling`), **Settle**, **Collect appeal rewards** (from the Dispute Resolver).

Full details, issue codes and the trust model are in `README.md`.

## Notes
- **Wrong-network risk (her request, 23 Oct; flipped on 27 Oct):** guests must send on **Ethereum mainnet**, NOT Arbitrum, Base, Optimism or any other network. ETH sent to the contract address on another network does not reach the contract and may be lost; say it plainly on Luma. The tx link should start with **https://etherscan.io/tx/** (see README "Guest instructions"). The owner wallet was already used on Arbitrum One (rehearsals), so ETH sent there to the contract address is most likely unrecoverable; keep the owner wallet off every other network (Base, Optimism, …) before settlement (see README "Wrong network").
- Guests must send the amount **in ETH** (not a dollar value), exactly the deposit, from their own wallet (not an exchange). The contract refuses ETH once the list is posted or the event is cancelled, so late ETH stays in the sender's wallet.
- **Post attendance list** is greyed out in the console until the event starts (her request, 23 Oct) and needs POST typed; **Release payouts** stays locked until the challenge window ends and no challenge waits for a match, and needs PAY typed. The contract enforces the same. Open Kleros cases don't block it (review F7): their shares are set aside.
- **Timing (on-chain):** the list can be posted from `eventStart` until `claimDeadline` (at least 7 days later; config uses 14). If no list is posted by then, each staker can withdraw their own deposit (`emergencyWithdraw`) in case the owner wallet is lost. After posting, anyone can call `releasePayouts`.
- **Payouts:** `postAttendance(attendees, share)` runs once; the share must match what she confirmed; challenges can add people, so the final share is pool ÷ final attendees. Each batch payment gives the wallet up to 40,000 gas (keeps 150 payments inside one mainnet transaction); if a wallet refuses ETH or needs more (some smart-contract wallets), that amount is kept in `owed` for the guest to `claim` to any address, and everyone else is still paid.
- **Appeal money** goes from each funder's own wallet to the Dispute Resolver (`fundAppeal(localDisputeID, side)`), never through our contract. Fund from a normal wallet (Zerion), not a Safe or smart-contract wallet: the Dispute Resolver pays refunds and rewards with a basic transfer and ignores failures.
- **Money nobody staked** (overpayments, stray transfers) can be returned with `refund`, which can never touch the staked pool, set-aside shares, challenge money or unclaimed payments. `sweep` collects rounding dust after settlement.
- **Tokens sent by mistake** (USDC, for example) are never deposits. She sends them back with **Return tokens sent by mistake** in the console (`returnToken`, moves no ETH); the verify script's `NO_DEPOSIT_TRANSFER` note names the token contract.
- **The contract counts money in total, not per wallet.** Only register wallets the verify script lists; registering an unverified wallet could use someone else's unregistered deposit.
- **Ownership** moves in two steps (`transferOwnership`, then `acceptOwnership` from the new wallet).
- **Test-network mode is gone** (27 Oct): only `config.json` (live) and `config.rehearsal.json` (throwaway rehearsal on mainnet). Tests run on a local ganache chain.
